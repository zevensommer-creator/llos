## 一、语音交互方案对比

### 方案 A：完整语音闭环

| 项 | 内容 |
|----|------|
| **范围** | STT（语音转文字）+ TTS（文字转语音）+ 发音评价 |
| **用户体验** | 学生说话 → 系统识别 → 训练反馈 → 语音输出 → 发音评分 |
| **技术复杂度** | **高**——需要对接 STT API、TTS API、发音评价引擎 |
| **核心难点** | 发音评价是重活，LLM 无法直接完成（详见第三节） |

**技术依赖**：
- STT 服务（Whisper API / Azure Speech / 讯飞）
- TTS 服务（Azure Speech / Edge TTS / 讯飞）
- 发音评价引擎（见第四节）
- 实时音频流处理（浏览器 MediaStream API 或客户端录音）

---

### 方案 B：部分语音（无发音评价）

| 项 | 内容 |
|------|------|
| **范围** | STT + TTS，不做发音评价 |
| **用户体验** | 学生说话 → 系统识别文字 → 训练反馈 → 语音输出。但系统不评价发音准确度 |
| **技术复杂度** | **中**——只需对接 STT 和 TTS API |
| **核心难点** | 无法评价"说得像不像"，只能评价"说的内容对不对"（语法/词汇层面） |

**技术依赖**：
- STT 服务
- TTS 服务
- 实时音频流处理

---

### 方案 C：文字优先，语音后续

| 项 | 内容 |
|------|------|
| **范围** | 第一版纯文字交互，语音作为 V2 迭代 |
| **用户体验** | 学生打字输入 → 训练反馈 → 文字输出 |
| **技术复杂度** | **低**——无需音频处理 |
| **核心难点** | 无法训练口语能力——而 LLOS 的核心场景之一就是口语训练 |

**技术依赖**：
- 无音频相关依赖

## 二、为什么发音评价是重活

发音评价（Pronunciation Assessment）和语音识别（STT）是**两个不同的问题**：

| 问题 | STT（语音识别） | 发音评价 |
|------|----------------|---------|
| 目标 | 用户说了什么？ | 用户说得好不好？ |
| 输出 | 文字 | 分数 + 错误位置 |
| 难度 | 中——大模型已成熟 | 高——需要音素级对比 |
| LLM 能否直接做 | ✅ 可以（Whisper 等） | ❌ 不能直接做（见第三节） |

发音评价需要：
1. **强制对齐**（Forced Alignment）：将用户音频与参考文本在音素级别对齐
2. **GOP 计算**（Goodness of Pronunciation）：计算每个音素的发音好坏
3. **错误定位**：标记哪个音素读错了，应该怎么纠正

这些都需要专门的声学模型，不是 LLM 的能力范围。

## 三、LLM 能否直接做发音评分？

**结论：不能直接做，存在根本性局限性。**

### 原因

1. **模态鸿沟**：音频信号是连续的波形，LLM 的输入是离散 token。LLM 无法直接"听"音频——它需要音频先被转成文字或特征向量，但这个转换过程会丢失发音细节（音高、时长、气息、口音等）。

2. **音素级感知不足**：即使多模态 LLM（如 SpeechGPT、AudioGPT）将音频离散化后输入，对音素级别的细微差异（如 /θ/ vs /s/，/r/ vs /l/）感知能力不足。

3. **缺少参考基准**：发音评分需要对比"标准发音"和"用户发音"的声学特征差异，这需要专门的声学模型计算似然分数，不是语言模型的能力。

### LLM 在发音评价中的正确角色

LLM **不应该**直接评分，但**可以**作为 pipeline 的上层决策层：

```
用户音频
  ↓
ASR/GOP 引擎（底层）→ 提取声学特征 + 评分 + 错误音素
  ↓
LLM（上层）→ 将评分结果转化为个性化教学反馈
  ↓
"你的 /θ/ 发成了 /s/，注意舌头放在牙齿之间"
```

即：**底层引擎打分，LLM 写评语**。

## 四、公开发音评价方案研究

### 4.1 云端 API 方案

#### Microsoft Azure Speech — Pronunciation Assessment（推荐）

| 项 | 内容 |
|----|------|
| **功能** | 准确度、流利度、完整度、韵律评分 |
| **粒度** | 音素级 + 词级 + 句子级 |
| **音素表示** | 支持 IPA 国际音标 |
| **语言支持** | 多语言（含中文 zh-CN） |
| **错误定位** | 标记哪段读错，返回每个音素分数 |
| **计费** | ~$1/分钟音频，有免费额度 |
| **开源示例** | Azure-Samples/cognitive-services-speech-sdk（Python/C#/JS/Java） |
| **文档** | https://learn.microsoft.com/azure/ai-services/speech-service/ |
| **适合度** | **LLOS 首选云方案**——功能最全面，多语言支持好，文档完善 |

#### 科大讯飞语音评测

| 项 | 内容 |
|----|------|
| **功能** | 准确度、流利度、完整度 |
| **接入** | REST API + Android/iOS/Web SDK |
| **语言** | 英语、中文 |
| **优势** | 国内服务延迟低，中文评测能力强 |
| **注意** | SDK 合规要求严格，需注意隐私政策 |
| **适合度** | 适合面向中国市场的中文评测场景 |

#### SpeechSuper

| 项 | 内容 |
|----|------|
| **功能** | 准确度、流利度、节奏、完整度 |
| **模式** | 跟读评分 / 半自由说 / 自由说（含语法+词汇评估） |
| **SDK** | 提供 iOS/Android 离线 SDK |
| **语言** | 8 种语言 |

### 4.2 开源方案

| 方案 | 底层 | 粒度 | GitHub | 可本地部署 | 说明 |
|------|------|------|--------|-----------|------|
| **Kaldi GOP** | GMM-HMM | 音素级 | Kaldi egs/gop | ✅ | 工业界经典 GOP 算法，流利说早期基础。门槛较高 |
| **Montreal Forced Aligner (MFA)** | Kaldi | Word + Phone | ~2k stars | ✅ | 最成熟的强制对齐工具，需发音词典。Windows 支持有限 |
| **Gentle** | Kaldi | Word + Phone | ~1.4k stars | ✅ (Docker) | 提供 REST API，仅做对齐不评分。可作为 GOP 前置步骤 |
| **torchaudio forced_align()** | Wav2Vec2 + CTC | Phone | PyTorch 内置 | ✅ | 现代 GPU 友好方案，需自行实现评分逻辑。API 将迁移至 TorchCodec |
| **WhisperX** | Whisper + Wav2Vec2 | Word | ~10k stars | ✅ | 词级时间戳对齐，可复用其对齐模块 |

### 4.3 技术原理简述

发音评价的标准流程：

```
用户音频 + 参考文本
       ↓
  特征提取（MFCC / Wav2Vec2）
       ↓
  强制对齐（Forced Alignment）
  → 将音频帧与参考文本的音素序列对齐
  → 得到每个音素的时间区间
       ↓
  GOP 计算（Goodness of Pronunciation）
  → 对比"受限识别"和"自由识别"的似然分数
  → GOP 值越高 = 发音越准确
       ↓
  错误定位
  → 对比对齐结果和自由识别结果
  → 标记错误音素
       ↓
  输出：{accuracy, fluency, completeness, phoneme_scores[]}
```

## 六、推荐架构

基于 LLOS 的 Core/DLC 分离原则，推荐**可插拔评分引擎**架构：

```
DLC 层
  └─ 定义评分配置（目标语言、评分维度、阈值、参考音频）
       ↓
Core 层
  └─ 调用评分引擎（可插拔，DLC 不感知具体实现）
       ↓
评分引擎（可切换实现）
  ├─ 云模式：Azure Speech PA（优先）
  ├─ 本地模式：Wav2Vec2 + torchaudio forced_align + GOP（Fallback）
  └─ 输出统一格式：{accuracy, fluency, completeness, phoneme_scores[]}
       ↓
LLM 层
  └─ 将评分结果转化为个性化教学反馈
     "你的 /θ/ 发成了 /s/，注意舌头放在牙齿之间"
```

### 关键设计

1. **DLC 定义评分配置**：目标语言、评分维度权重、阈值、标准参考音频
2. **Core 调用可插拔引擎**：DLC 不感知底层用的是 Azure 还是 Wav2Vec2
3. **云优先 + 本地 Fallback**：有网络时用 Azure（精度高），无网络时用 Wav2Vec2（免费）
4. **LLM 只做反馈生成**：不直接评分，将引擎输出的结构化评分转为自然语言教学反馈
